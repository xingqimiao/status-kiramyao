# status.kiramyao.com on a Cloudflare Worker

The status page is served by the same box it monitors, so it cannot report that box being
down, and its probes run from inside the thing they probe. This directory moves the page to
a Worker, the probes to Cloudflare's edge, and the history to D1 -- while the Node service
keeps running unchanged until the Worker is verified.

The page is rendered by the *same* `lib/view.mjs`, with the *same*
`lib/components.mjs` register and the *same* `lib/aggregate.mjs` /
`lib/incidents.mjs` rules.

## The probe freshness contract

There is **no grey-cloud record, no DNS-only host, and no origin bypass**. Every probe goes
to the normal proxied hostname, and the response itself has to prove it was generated by the
origin for *this* request rather than replayed by some cache. Three layers, none sufficient
alone:

| layer | what it is | what it stops |
|---|---|---|
| 1. unique URL + request bypass | `?nonce=<random>` per probe (the query string is part of the cache key), `cf: { cacheTtl: 0, cacheEverything: false }`, `Cache-Control: no-cache` | a stored copy under another URL; Cloudflare reusing or storing this URL |
| 2. non-reusable response | the origin sends `Cache-Control: no-store` (or `max-age=0`) and `Pragma: no-cache` | a cache holding the response for reuse |
| 3. nonce echo | app endpoints reflect the exact random nonce (body or `X-Probe-Nonce`) | **any** layer replaying an older response -- a cache cannot know a value minted for this request |

A 200 that fails layer 2 or 3 is recorded as a **failure**, not a pass. `cf-cache-status:
HIT|STALE` or `Age > 0` is also a failure. All three are enforced in
`worker/src/probe.mjs` and each has a test.

### Which hosts can give the hard proof, and which cannot

| component | host | nonce echo | honesty bound |
|---|---|---|---|
| comments_api | api.kiramyao.com/comments/health | yes, once the origin echoes | full: nonce echoed |
| hrt_api | api.kiramyao.com/hrt/health | yes, once the origin echoes | full |
| hrt_mcp | api.kiramyao.com/hrt/mcp/health | yes, once the origin echoes | full |
| hrt_web | hrt.kiramyao.com/ | **no** -- static file serving | unique URL + non-reusable response only |
| site_overseas | kiramyao.com/ | **no** -- static (Pages) | unique URL + non-reusable response only |

**Stated limitation, not hidden:** for `hrt_web` and `site_overseas` a cache that
keyed on something other than the full URL could in principle replay a copy and the probe
could not tell. Layers 1 and 2 are the *entire* guarantee there. We do not pretend they are
the nonce proof. The origin contract asks static paths to add `no-store`;
`kiramyao.com` already sends `public, max-age=0, must-revalidate`, which the probe
accepts as equivalently non-reusable.

Live observation on 2026-09-21, requesting each URL with a nonce query (through a local HTTP
proxy; status and header values are what matter here, not timing):

* API endpoints: `Cache-Control: no-store`, `cf-cache-status: DYNAMIC`, no nonce
  echo yet -> layer 2 already satisfied, layer 3 needs the origin patch.
* `kiramyao.com`: `Cache-Control: public, max-age=0, must-revalidate`,
  `cf-cache-status: DYNAMIC`.
* `hrt.kiramyao.com`: **no `Cache-Control` at all**, `cf-cache-status:
  DYNAMIC` -> needs the Caddy header; see `ORIGIN-CONTRACT.md`.

Because the nonce is absent from the live API responses, those three rows read **red** until
the origin patch is applied. That is deliberate: the alternative is a green with no evidence.

**Measurement caveat.** This development machine resolves the kiramyao hostnames to
`198.18.x.x` (a local proxy's fake-IP range), so any latency or timeout observed here is
proxy-polluted and must not drive a design decision -- an earlier `hrt.kiramyao.com` stall was
exactly that and was a false alarm (the owner's side was fine). Header and status-code
observations are unaffected in substance, but re-confirm on the box if in doubt.

## Always Online

**Status: OFF. Confirmed by the owner in the Cloudflare dashboard on 2026-09-21.** This is a
recorded human observation, not a value this agent read: no Cloudflare API credential was
available here (no `CLOUDFLARE_*` / `CF_*` / zone env var, no `~/.cloudflared` or
`~/.cloudflare`, and the repo `.env` holds only `BOCE_API_KEY`), and a value that was
not observed was not asserted.

To re-read it independently (token needs **Zone Settings:Read**):

```bash
curl -s -H "Authorization: Bearer $CF_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/settings/always_online" | jq .result.value
```

or Dashboard: Zone -> Caching -> Configuration -> Always Online.

Why it mattered, and why "off" is the right state: Always Online serves a Cloudflare-cached
copy of **cacheable** content when the origin is unreachable -- exactly the "origin is down but
the page looks fine" failure this probe design exists to prevent. It can only replay something
Cloudflare actually stored, and our probes use a fresh `?nonce=` URL each time (no entry under
that key) with a non-reusable response (nothing stored), so it could not fabricate a fresh 200
for a probe URL; every live request came back `cf-cache-status: DYNAMIC`. It is kept off
anyway because it is zone-level and its blast radius is not limited to these probe paths.
Recording the value remains a cutover precondition; the value to record is now **off (owner,
dashboard, 2026-09-21)**.

## Cron granularity: 10 minutes is available

Cloudflare cron expressions are five fields with a `0-59` minute field; the documented
examples include `* * * * *` and `*/30 * * * *`. The minimum granularity is one
minute, and `*/10 * * * *` is valid on both plans. The constraints a 10-minute schedule
actually hits are the Free plan's **5 triggers per account** and **10 ms CPU** per Cron
invocation (paid 30 s); the design stays inside them by grouping days in SQL rather than
reading every row. Cron executes in UTC; the page still cuts days at GMT+8.

## D1: the schema, and what changed

The schema is `worker/migrations/0001_init.sql`; apply it with
`npx wrangler d1 migrations apply kira-status --remote`. Two forced changes from
`lib/db.mjs`:

* **`PRAGMA journal_mode = WAL` is gone** -- D1 supports only a fixed PRAGMA allow-list
  and manages durability itself.
* **`AUTOINCREMENT` is gone** -- `INTEGER PRIMARY KEY` is already the rowid alias.

The two history tables keep their exact column names, so the SELECT/INSERT statements port
with only the async calling convention changed. The reads changed shape:

* **Aggregate reads.** `allProbes(since)` returned every row; at 10-minute cadence over
  90 days that is ~13,000 rows per component, and D1 charges CPU for result serialization
  inside a 10 ms budget. `worker/src/db.mjs` issues five bounded queries: per-day counts
  (~450 rows), newest round per component (<= 5), **runs collapsed in SQL** (a healthy window
  is one row per component), failing probes only, and the newest metric per key.
* **`incidentsFromRuns`.** `lib/incidents.mjs` was split so run-collapsing and the
  incident arithmetic are separate; SQL produces the runs and the shared rule consumes them.

The port is asserted, not trusted: `worker/test/port.test.mjs` seeds one database and
runs it through both `lib/snapshot.mjs` and `worker/src/snapshot.mjs`, comparing
field for field (including the GMT+8 midnight boundary, a flap, a silence, out-of-order rows).

### The migration step

```bash
node bin/export-d1.mjs --days=90 > /tmp/status.sql
npx wrangler d1 execute kira-status --remote --file /tmp/status.sql
```

`events` is deliberately not exported; manual declarations are authored through the
admin. Import into an empty database created by the migration and compare `COUNT(*)`.

## The probes: measured outside the zone

The cron does **not** probe inbound. A Worker subrequest to a hostname in the same zone
that proxies to a real origin times out -- measured from D1, `site_overseas` (answered by
Cloudflare) came back while `hrt_web`, `hrt_api`, `hrt_mcp` and `comments_api` all recorded
`timeout after 4000ms`. A cron that ran anyway wrote the same five false reds every ten
minutes. It no longer runs a probe round at all: an out-of-zone prober measures these five
targets and reports through `POST /ingest/probe` (`worker/src/ingest.mjs`;
`ORIGIN-CONTRACT.md` sections 10-11). Its rows carry `source = 'external'`.
`runWorkerProbeRound` stays in `worker/src/probe.mjs` because the freshness tests use it
against a local origin. Rows the old cron already wrote keep `source = 'local'` and are not
rewritten; they age out with the 90-day prune. The live state and the incident list follow
the newest row, which from cutover on is external.

| component | target | nonce echo |
|---|---|---|
| `site_overseas` | `https://kiramyao.com/.well-known/status-probe.txt` | no (Pages) |
| `hrt_web` | `https://hrt.kiramyao.com/.well-known/status-probe.txt` | no (static) |
| `hrt_api` | `https://api.kiramyao.com/hrt/health` | **yes** |
| `hrt_mcp` | `https://api.kiramyao.com/hrt/mcp/health` | **yes** |
| `comments_api` | `https://api.kiramyao.com/comments/health` | **yes** |

**The China probe runs on the out-of-zone prober, not here.** `runBoceProbe` is not
imported into the Worker: the adapter is a create call plus an async poll (up to ~2
minutes), which does not fit a cron invocation, and the credential stays box-side. The
prober takes one 28-node boce sample per Beijing day -- gated by a state file, so never a
second sample in a day -- and appends the per-node rows to the same `POST /ingest/probe`
round as the five inbound readings, so a round is still one atomic write (and a retry
inside that round's ten-minute bucket re-appends the CN rows rather than erasing them).
`site_cn` is therefore in the ingest's allowed component set: the register, not only the
local probe loop. `BOCE_ENABLED=true` (`wrangler.toml`) is what tells the snapshot a CN
sample is expected -- a day that produced none is capped at amber rather than read green,
and the row goes stale on the daily cadence instead of the ten-minute one.

Guardian reads keep every rule: only a value actually read is written ("—", never 0);
`readStoryCount` refuses to report zero stories from a parsed-but-empty catalogue;
`readCloudflareVisits` strips the port, sums a host across rows, and treats HTTP 200
with an `errors` array as a failure.

## Origin heartbeat

`POST /heartbeat`, `Authorization: Bearer <HEARTBEAT_TOKEN>` (or
`X-Heartbeat-Token`). The origin pushes what no outside probe can see:

```json
{ "postgres": { "ok": true, "latency_ms": 12 }, "disk": { "used_pct": 63.4, "free_gb": 41.2 } }
```

Closed schema: three allowed top-level keys, three nested keys, boolean/number types, range
checks, a 4 KiB cap and a clock-skew check; unknown keys are a 400. It writes a fixed set of
metric keys (`origin.postgres_ok`, `origin.*`, `origin.heartbeat_at`) and
nothing else. There is no free-text field, so a stolen token can distort two numbers and the
timestamp but **cannot put a sentence on the page**. A stale heartbeat (> .
`HEARTBEAT_STALE_MINUTES`) renders "—". The heartbeat answers "is the box alive"; the
inbound probes answer "can it serve". Both are kept because they are independent signals.

The push is a systemd timer on the origin box, `kira-status-heartbeat.timer`
(`OnCalendar=*:0/2`), running `/usr/local/bin/kira-status-heartbeat.sh`: a `SELECT 1`
timed by psql itself, and `df -P /`. A check that fails sends `ok:false` and omits its
number -- the schema has room for null and the page renders "—", so a failing check can
never arrive as a fabricated 0. Only the disk reading has a tile on the page; the Postgres
facts are still recorded and carried in `/history.json`.

## Inbound probes: the out-of-zone prober

`POST /ingest/probe`, `Authorization: Bearer <PROBE_TOKEN>` (a Worker secret). The prober
runs the three-layer contract from a shell -- a fresh `?nonce=` per request, a required
non-reusable response, and the nonce echo on the three app endpoints -- and reports the
verdict for each of the five targets:

```json
[
  { "component": "site_overseas", "ok": true, "status_code": 200, "latency_ms": 84 },
  { "component": "hrt_web", "ok": true, "status_code": 200, "latency_ms": 91 },
  { "component": "hrt_api", "ok": true, "status_code": 200, "latency_ms": 120 },
  { "component": "hrt_mcp", "ok": true, "status_code": 200, "latency_ms": 133 },
  { "component": "comments_api", "ok": true, "status_code": 200, "latency_ms": 99 }
]
```

A JSON array of up to 50 rows; only `component` (a registered id), `ok` (boolean),
`status_code` (100..599 or null), `latency_ms` (0..120000 or null) and `error` (a string
of at most 200 characters, or null) are accepted. An unknown key is a 400; a wrong or
missing token is a 401, never a redirect. The Worker stamps the whole round with one `at`
-- its clock rounded down to the 10-minute cadence -- and replaces any `source='external'`
rows already at that `at`, so the prober can retry a round without doubling it. A shell
implementation is in `ORIGIN-CONTRACT.md` section 10; run it every 10 minutes.

## Manual declarations behind Cloudflare Access

### The policy

The Access application is attached to the **hostname** `status.kiramyao.com` with a path
rule for `/admin*`. Because that does not cover the Worker's other ingresses,
`workers_dev = false` and `preview_urls = false` are set, **and** the Worker
verifies the assertion itself and returns **403, never a redirect**, on failure.

### The JWT check

`Cf-Access-Jwt-Assertion` -> read `kid`, fetch the team JWKS once per isolate
(10-minute cache), import the RSA key with WebCrypto (`RSASSA-PKCS1-v1_5`/SHA-256),
verify the signature over `header.payload`, then require `iss` = the team domain,
`aud` contains `ACCESS_AUD`, and `exp` (and `nbf`) are valid. The audit
identity is Access's own `email`/`sub` claim.

### Manual vs probe: the rule

**A manual declaration may raise severity; it may never lower it.** `/admin` publishes an
event with severity (`partial` -> amber, `full` -> red, `maintenance` ->
amber), a reason, and an effective time; it stays in force until **宣判恢复** writes
`resolved_at`. The banner is `worse(probeState, manualState)`, and "no active
declaration" is `grey` (below green), so a recovery cannot hide a red probe. The page
shows the severity, the reason verbatim, the **GMT+8** start time, the publisher, and a second
line `自动探测：<verdict>`; when they disagree it adds `（与人工宣判不一致）`. If the
latest declaration is resolved but probes still fail: `运维已宣判恢复，但自动探测仍显示「…」。`.
`/history.json` carries `probe_overall` and `manual`.

## What was preserved from the incident list

* **Days cut at GMT+8** -- `STATUS_UTC_OFFSET_MS` is imported and used in the D1 grouping.
* **Unreadable shows "—", never 0** -- missing metrics and stale heartbeats are `null`.
* **A span is measured, not configured.** `windowDays` (per row and for the page) and
  `availabilityHint` come from the first GMT+8 day that has a reading, capped at
  `HISTORY_DAYS`: a four-day-old deployment says four days, a row that started later says
  its own shorter span, and a full window still says the full window. The strip keeps
  drawing the whole window so a day with no reading still holds its cell; only the
  numbers that name a span are shortened. `历史数据保留 N 天` is retention, not a reading,
  and stays at `HISTORY_DAYS`.
* **The footer states the delay and the zone** -- unmodified `lib/view.mjs`.
* **Hosts are normalised by stripping the port**, unchanged.
* **A GraphQL error is HTTP 200 with an `errors` array**, checked before the data.
* **No third-party request from the reader's browser** -- same CSP, inline styles, same-origin
  icons, no scripts; the admin page is script-free too.

## Cutover (no big bang)

1. **Apply the origin contract** (`ORIGIN-CONTRACT.md`, pinned): echo the nonce on the three
   API health routes; add a non-reusable `Cache-Control` to the two
   `/.well-known/status-probe.txt` static paths. Until this is done the affected rows read red
   by design.
2. **Always Online**: recorded as **off** (owner, dashboard, 2026-09-21). Re-read it with the
   command above if the zone changes; it must be off at cutover.
3. `npx wrangler d1 create kira-status`; put the id in `wrangler.toml`.
4. Create the Access application for `status.kiramyao.com/admin`; set secrets
   (`ACCESS_AUD`, `HEARTBEAT_TOKEN`, `PROBE_TOKEN`, optionally
   `CF_ANALYTICS_TOKEN`/`CF_ZONE_TAG`).
5. `npx wrangler d1 migrations apply kira-status --remote`, then export and import history.
   `bin/export-d1.mjs` is read-only on the origin; the Node service keeps running.
6. Deploy to a **staging hostname** and compare pages (the port test is the automated version).
7. **Acceptance test**: stop one origin service and confirm the page turns red within one cron
   interval (10 minutes; plus at most 60 s of `Cache-Control` on the page). Only then
   attach the custom domain `status.kiramyao.com`.
8. **Rollback**: re-point the `status` record at the box, re-enable the Caddy block,
   `systemctl start kira-status`. Origin history was never modified.

## Verification run for this change

```bash
npm test                                   # 138 pass (84 origin + 54 worker)
node worker/verify-freshness.mjs           # the live three-layer check, one command
cd worker && npx wrangler deploy --dry-run --outdir .dry-run
node bin/export-d1.mjs --days=90 | Select-Object -First 4
```

The acceptance test (`worker/test/freshness.test.mjs`) runs a real local HTTP origin,
probes it green, **stops the server**, runs the next round and asserts the snapshot is red.
On this machine it measured **stopped -> red snapshot in 11-19 ms** (across runs) at the next
round; the page is red within one 10-minute cron tick plus the 60 s page cache.

The probe tests cover each layer: a unique nonce URL and the `cf` cache options on the
request; a 200 without `no-store` is a failure; `cf-cache-status: HIT` is a failure;
`Age > 0` is a failure; a 200 that does not echo the nonce is a failure; and a genuine
fresh, echoing, non-reusable response passes.

After the origin patch is live, one command proves all three layers against the real hosts:

```bash
node worker/verify-freshness.mjs
```

It sends two probes per endpoint so the nonces must differ (layer 1), prints the observed
`Cache-Control` / `cf-cache-status` / `Age` and whether the nonce came back (layers 2
and 3), and exits non-zero if any required layer fails. It uses Node's fetch, so the
Worker-only `cf: { cacheTtl: 0 }` cannot be exercised from a laptop -- that part is asserted by
`worker/test/probe.test.mjs`.
